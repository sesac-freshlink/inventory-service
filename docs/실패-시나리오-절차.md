# 실패 시나리오 절차 (T-23)

쪽지 처리에 실패했을 때 재고가 어떻게 남는지, DLQ에 간 쪽지를 어떻게 다시 보내는지 정리한다. PC에서 자동으로 확인할 수 있는 것은 테스트로 만들었고, SQS가 있어야 하는 것(DLQ 도착·재전송)만 여기 절차로 적는다.

명령은 Windows PowerShell 5.1 기준이다. AWS 로그인·포트 포워딩·실행 구성은 [개발 환경 접속 가이드](https://github.com/sesac-freshlink/.github/blob/main/docs/팀원-가이드/0-개발환경-접속.md) 1~4장을 따른다. 비밀값은 이 문서에 적지 않는다.

## 1. 자동 테스트로 확인하는 것

`src/test/java/com/freshlink/inventory/FailureScenarioTest.java`가 확인한다. `./gradlew build`(Windows는 `gradlew.bat build`)에 포함되고 Docker Desktop이 켜져 있어야 한다.

| 시나리오 | 기대 |
|---|---|
| 결제 실패 RELEASE(PAYMENT_FAILED) 뒤 같은 주문 CONFIRM | 재고 그대로, 에러 로그 1건, 쪽지는 정상 처리 |
| 10분 미결제 RELEASE(EXPIRED) 뒤 새 주문 RESERVE | 되돌린 수량을 새 주문이 잡는다 |
| 상품코드 없는 INBOUND | `BusinessException(PRODUCT_NOT_FOUND)`를 던지고 `processed_message`·`inbound`·lot이 모두 롤백된다 |
| 같은 INBOUND 재전송(같은 shipmentId, 새 messageId) | 한 번만 입고한다 |
| DISPOSE 처리 때 수량 부족 | disposal SKIPPED, 재고 그대로 |
| 알 수 없는 type JSON | `MessageJson.fromJson`과 리스너가 예외를 던진다(DLQ 경로) |
| RESERVE 수량 0 | RESERVE_FAILED `INVALID_QUANTITY` |
| 상품코드 없는 INBOUND가 3번 실패 → 상품 보정 → 같은 본문 재처리, 한 번 더 겹쳐 옴 | 한 번만 입고(lot 10, 원장 INBOUND 1줄, `processed_message` 1줄). 두 번째는 건너뛴다 |

예외를 던진 쪽지는 SQS에서 지워지지 않는다. 가시성 시간 초과가 지나면 다시 오고, 3번 실패하면 DLQ로 옮겨진다. 처리와 `processed_message` 기록이 한 트랜잭션이라 실패한 쪽지는 기록도 남지 않는다. 그래서 원인을 고친 뒤 같은 쪽지를 다시 보내면 정상으로 처리된다.

### 1-1. 실패 로그로 쪽지 찾기

리스너는 예외를 던지기 전에 쪽지 정보를 한 줄로 남긴다(`InventoryCommandListener`). Spring Cloud AWS가 찍는 `Error processing message …`에는 SQS 쪽 ID만 있어서 쪽지 본문의 번호로는 찾을 수 없기 때문이다.

```text
WARN  쪽지 처리 실패 type=RESERVE messageId=… storeId=5 orderId=501 productId=16 quantity=2 receiveCount=1/3 이유=IllegalStateException: …
ERROR 쪽지 처리 실패 type=RESERVE messageId=… storeId=5 orderId=501 productId=16 quantity=2 receiveCount=3/3 (DLQ로 간다) 이유=…
ERROR 쪽지 본문을 읽지 못함 receiveCount=3/3 (DLQ로 간다) 이유=… 본문={"type":"NOPE",…}   ← 앞 300자만
```

- `receiveCount`는 SQS가 이 쪽지를 몇 번째 내줬는지다. 마지막 시도(`app.queue.max-receive-count`, 기본 3. infra `maxReceiveCount`와 같게 둔다)면 ERROR, 그 전이면 SQS가 다시 보내므로 WARN이다. `DLQ로 간다`로 찾으면 DLQ로 간 쪽지만 나온다(Spring Cloud AWS의 `Error processing message`는 시도마다 ERROR로 찍혀서 그 수와는 다르다).
- 종류마다 남기는 번호: RESERVE `orderId productId quantity`, CONFIRM `orderId`, RELEASE `orderId reason`, INBOUND `shipmentId productCodes`, DISPOSE `disposalId lotId quantity`.
- DLQ 채널 알림(`.github` [가이드 6](https://github.com/sesac-freshlink/.github/blob/main/docs/팀원-가이드/6-디스코드-알림.md) 4장)이 오면 DLQ 본문의 `messageId`나 `orderId`로 Loki에서 찾는다.

```text
{namespace="freshlink", app="inventory-service"} |= "쪽지 처리 실패" |= "orderId=501"
{namespace="freshlink", app="inventory-service"} |= "DLQ로 간다"
```

원인을 고친 뒤 재처리는 가이드 6 5장(공용 dev 큐) 또는 아래 4장(개인 큐) 순서를 따른다. RESERVE는 5장을 먼저 본다.

## 2. 큐 이름

| 큐 | 개인(`dev-taewoo-`) | 공용(`dev-`, dev 클러스터) |
|---|---|---|
| 명령 (FIFO) | `dev-taewoo-inventory-commands.fifo` | `dev-inventory-commands.fifo` |
| 명령 DLQ | `dev-taewoo-inventory-commands-dlq.fifo` | `dev-inventory-commands-dlq.fifo` |
| 결과 | `dev-taewoo-inventory-results` | `dev-inventory-results` |
| 결과 DLQ | `dev-taewoo-inventory-results-dlq` | `dev-inventory-results-dlq` |

결과 큐(RESERVED·RESERVE_FAILED)는 order-service가 읽는다. 결과 DLQ는 order 쪽에서 다룬다. 아래 절차는 개인 명령 큐 기준이다. PC에서는 공용 큐를 쓰지 않는다.

## 3. 준비

```powershell
$env:AWS_PROFILE = "freshlink-dev"
$cmd = aws sqs get-queue-url --queue-name dev-taewoo-inventory-commands.fifo --query QueueUrl --output text
$dlq = aws sqs get-queue-url --queue-name dev-taewoo-inventory-commands-dlq.fifo --query QueueUrl --output text

# 재시도 횟수(maxReceiveCount)와 가시성 시간 초과 확인. DLQ 도착까지 대략 가시성 시간 초과 × 3이 걸린다
aws sqs get-queue-attributes --queue-url $cmd --attribute-names RedrivePolicy VisibilityTimeout
```

PC inventory를 `QUEUE_PREFIX=dev-taewoo-`로 띄운다(접속 가이드 3장). 로그에 `Started InventoryServiceApplication`이 나와야 쪽지를 가져간다.

## 4. 상품코드 없는 INBOUND → DLQ → 재전송

### 4-1. 실패하는 쪽지 보내기

```powershell
$id = [guid]::NewGuid().ToString()
@"
{"messageId":"$id","type":"INBOUND","createdAt":"2026-10-25T10:00:00+09:00","storeId":1,"shipmentId":"SHP-T23-NOCODE-001","items":[{"productCode":"P999","quantity":5,"expiryDate":"2026-11-30"}]}
"@ | Set-Content inbound-nocode.json -Encoding Ascii

aws sqs send-message --queue-url $cmd --message-body file://inbound-nocode.json --message-group-id 1 --message-deduplication-id $id
```

- JSON은 파일(`file://`)로 넘긴다. PowerShell 5.1은 명령줄로 넘긴 JSON의 따옴표를 지운다.
- PC 로그에 `INBOUND 상품 조회 실패: shipmentId=SHP-T23-NOCODE-001, productCode=P999`와 `쪽지 처리 실패 type=INBOUND … receiveCount=1/3`이 3번 찍힌다. 세 번째 줄은 ERROR이고 `(DLQ로 간다)`가 붙는다.
- 같은 점포(그룹 `1`)의 다음 쪽지는 이 쪽지가 DLQ로 갈 때까지 기다린다(FIFO 순서). 시험 중에는 점포 1에 다른 쪽지를 보내지 않는다.

### 4-2. DLQ 도착 확인

```powershell
aws sqs get-queue-attributes --queue-url $dlq --attribute-names ApproximateNumberOfMessages
aws sqs receive-message --queue-url $dlq --visibility-timeout 0 --wait-time-seconds 10 --query "Messages[].Body"   # 보기만 한다. 가시성 0이라 바로 재전송할 수 있다
```

`ApproximateNumberOfMessages`가 1이고 본문의 `shipmentId`가 `SHP-T23-NOCODE-001`이면 된다. DB에서는 `inbound`·`processed_message`에 이 쪽지 기록이 없어야 한다.

```sql
SELECT COUNT(*) FROM inbound WHERE shipment_id = 'SHP-T23-NOCODE-001';     -- 0
SELECT COUNT(*) FROM processed_message WHERE message_id = '<위 $id 값>';   -- 0
```

### 4-3. 원인 고치고 다시 보내기

운영에서는 상품 데이터를 보정한 뒤(E-12 담당) 재전송한다. dev RDS를 직접 고치지 않으므로 이 시험에서는 재전송이 동작하는지만 본다. 상품이 여전히 없으므로 쪽지는 다시 3번 실패하고 DLQ로 돌아온다.

`start-message-move-task`는 쪽지 하나가 아니라 **DLQ에 있는 쪽지 전부**를 옮긴다. 4-2에서 받은 한 건이나 `ApproximateNumberOfMessages`(대략값)만으로는 DLQ에 시험 쪽지만 있다고 확신할 수 없다. 이 명령은 개인 DLQ(`dev-taewoo-…-dlq.fifo`)에 이 시험 쪽지만 넣었을 때만 쓴다. 다른 쪽지가 섞였을 가능성이 있으면 옮기지 않는다. 그때는 4-4처럼 시험 쪽지만 꺼내 확인하고, 다시 보내야 하면 그 본문을 4-1 방식으로 원래 큐에 새로 보낸 뒤 DLQ의 그 쪽지를 지운다.

```powershell
$arn = aws sqs get-queue-attributes --queue-url $dlq --attribute-names QueueArn --query Attributes.QueueArn --output text
aws sqs start-message-move-task --source-arn $arn
aws sqs list-message-move-tasks --source-arn $arn   # Status가 COMPLETED면 옮기기 끝
```

- 목적지를 주지 않으면 쪽지가 원래 큐(`dev-taewoo-inventory-commands.fifo`)로 돌아간다. 본문(JSON)의 `messageId`는 그대로라 inventory의 멱등 처리 기준도 같다. SQS가 붙이는 `MessageId`는 새로 발급된다.
- PC 로그에 같은 `상품 조회 실패`가 다시 찍히고, 잠시 뒤 DLQ 개수가 다시 1이 되면 재전송 경로가 확인된 것이다.
- 상품이 보정된 경우라면 이번에는 정상 입고되고 `inbound`에 `SHP-T23-NOCODE-001` 행이 생긴다.

### 4-4. 시험 쪽지 치우기

DLQ에 남은 시험 쪽지 하나만 지운다. `purge-queue`는 다른 쪽지까지 전부 지우고 되돌릴 수 없으므로 쓰지 않는다.

```powershell
$msg = aws sqs receive-message --queue-url $dlq --max-number-of-messages 1 --visibility-timeout 60 --wait-time-seconds 10 --output json | ConvertFrom-Json
if ($null -eq $msg -or $null -eq $msg.Messages -or @($msg.Messages).Count -ne 1) { throw "DLQ에서 쪽지를 받지 못했다. 다시 실행한다" }
$m = @($msg.Messages)[0]
$m.Body
# 시험 쪽지인지 본문으로 확인한다. 다른 쪽지면 지우지 않고 멈춘다(60초 뒤 DLQ에 다시 보인다)
$b = try { $m.Body | ConvertFrom-Json } catch { $null }
if ($null -eq $b -or $b.shipmentId -ne "SHP-T23-NOCODE-001") { throw "시험 쪽지가 아니다. 지우지 않는다" }
aws sqs delete-message --queue-url $dlq --receipt-handle $m.ReceiptHandle
```

## 5. RESERVE가 DLQ에 갔을 때

RESERVE는 **주문이 아직 RESERVING일 때만** 다시 보낸다(명세 5-3 1번, order와 합의).

1. DLQ 본문에서 `orderId`를 확인한다.

   ```powershell
   aws sqs receive-message --queue-url $dlq --visibility-timeout 0 --wait-time-seconds 10 --query "Messages[].Body"
   ```

2. order-service 담당(김경우)에게 그 주문 상태를 확인한다.
   - **RESERVING**: 원인을 고친 뒤 4-3처럼 `start-message-move-task`로 재전송한다. 같은 orderId 예약이 이미 있으면 inventory가 같은 RESERVED를 다시 보내므로 두 번 잡히지 않는다.
   - **그 밖(수동으로 닫힌 주문 등)**: 재전송하지 않는다. 다시 보내면 닫힌 주문에 재고가 잡힌다. 아래 3번으로 그 쪽지 하나만 지운다.
3. 버릴 RESERVE 쪽지 하나만 지운다. 4-4는 시험 쪽지(`SHP-T23-NOCODE-001`)만 지우게 되어 있으므로 쓰지 않는다. 지울 orderId를 넣고, 받은 쪽지가 그 주문의 RESERVE인지 확인한 뒤에만 지운다. 다른 쪽지가 오면 지우지 않고 멈추고, 60초 뒤 다시 실행한다.

   ```powershell
   $dropOrderId = 0     # ← 버릴 주문의 orderId로 바꾼다
   if ($dropOrderId -le 0) { throw "dropOrderId를 바꾼다" }
   $msg = aws sqs receive-message --queue-url $dlq --max-number-of-messages 1 --visibility-timeout 60 --wait-time-seconds 10 --output json | ConvertFrom-Json
   if ($null -eq $msg -or $null -eq $msg.Messages -or @($msg.Messages).Count -ne 1) { throw "DLQ에서 쪽지를 받지 못했다. 다시 실행한다" }
   $m = @($msg.Messages)[0]
   $b = try { $m.Body | ConvertFrom-Json } catch { $null }
   if ($null -eq $b -or $b.type -ne "RESERVE" -or $b.orderId -ne $dropOrderId) { throw "버릴 RESERVE가 아니다. 지우지 않는다: $($m.Body)" }
   aws sqs delete-message --queue-url $dlq --receipt-handle $m.ReceiptHandle
   ```

4. DLQ에 다른 쪽지가 같이 있으면 `start-message-move-task`는 전부 옮긴다. 버릴 쪽지를 3번으로 먼저 모두 지운 뒤 옮긴다. 남은 쪽지가 모두 재전송해도 되는 것인지 4-2 방식으로 본문을 확인한다.

## 6. CONFIRM·RELEASE·DISPOSE

- CONFIRM에 예약이 없거나 해제된 주문은 DLQ로 가지 않는다. 에러 로그(`CONFIRM 반영 안 함`)만 남기고 정상 처리한다. 로그를 보고 order 담당과 원인을 맞춘다.
- RELEASE에 해제할 예약이 없으면 info 로그만 남긴다.
- DISPOSE는 disposal 행이 없을 때만 예외(DLQ)다. 수량이 모자라면 SKIPPED로 정상 처리한다.
