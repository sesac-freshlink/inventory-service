# 고객용 재고 조회 표 (CQRS)

고객 상품 목록(U-10)은 매번 lot을 합산하지 않고, 미리 계산해 둔 조회 전용 표 `store_product_stock`을 읽는다. 재고를 바꾸는 쪽(쓰기)과 고객이 읽는 쪽(읽기)의 표를 나눈 것이라 CQRS(Command Query Responsibility Segregation)라고 부른다. 같은 DB, 같은 서비스 안에서 나눴다.

## 1. 한 문단 설명

> 고객 상품 목록은 매번 lot을 합산하지 않고 조회 전용 표를 읽습니다. 재고를 바꾸는 처리가 같은 트랜잭션에서 그 표도 다시 계산해 두기 때문에 둘이 어긋나지 않습니다. 유통기한은 쪽지 없이 시간이 지나면 바뀌므로, 표에 "이 값이 맞는 시각"을 같이 두고 그 시각이 지나면 품절로 보여 준 뒤 1분 정리 작업이 바로잡습니다.

## 2. 구조

```
재고를 바꾸는 처리 (입고·예약·확정·해제·폐기 쪽지, 수동 조정 API)
   │ 처리 끝에서 한 줄: stockChanges.publish(storeId, 바뀐 상품들)
   ▼
StockChangePublisher ── 그 상품의 lot을 잠금 읽기(FOR SHARE)로 합산 ──► StockChanged 이벤트
   ▼ (스프링 이벤트, 같은 스레드·같은 트랜잭션)
StoreStockProjector ── upsert 한 문장 ──► store_product_stock
                                              ▲
고객 상품 목록 GET /stores/{storeId}/products ─┘ (이 표만 읽는다)

StoreStockRefreshScheduler (1분, ShedLock) ── 값이 맞는 시각이 지난 행만 다시 publish
```

| 파일 | 하는 일 |
|---|---|
| `domain/storestock/StockChangePublisher` | lot을 합산해 이벤트를 낸다. 재고를 바꾸는 처리가 부르는 유일한 입구 |
| `domain/storestock/StockChanged` | 이벤트. 점포·상품·구매 가능 수량·값이 맞는 시각. 변화량이 아니라 결과값 |
| `domain/storestock/StoreStockProjector` | 조회 표에 쓰는 유일한 곳 |
| `domain/storestock/StoreProductStock` | 조회 표 한 행. `availableAt(now)`가 "시각이 지났으면 0" 규칙을 가진다 |
| `domain/storestock/StoreStockRefresher`, `domain/scheduler/StoreStockRefreshScheduler` | 1분 정리 |
| `domain/inventory/InventoryQueryService#getStoreProducts` | 고객 목록. 조회 표만 읽는다 |
| `db/migration/V6__store_product_stock.sql` | 표 생성과 기존 lot으로 미리 채우기 |

## 3. 규칙 세 개

1. **쓰기:** 재고를 바꾼 처리는 끝에서 그 상품의 구매 가능 수량을 lot에서 다시 계산해 조회 표에 넣는다. 같은 트랜잭션이다. 처리가 실패해 되돌려지면 조회 표도 같이 되돌려진다.
2. **읽기:** 고객 목록은 조회 표만 읽는다. 행의 `valid_until`(이 값이 맞는 마지막 시각)이 지났으면 그 상품은 품절(0)로 보여 준다. 행이 없는 상품도 0이다.
3. **정리:** 1분마다 `valid_until`이 지난 행을 lot에서 다시 계산한다.

구매 가능 수량의 정의는 점주 화면·예약과 같다: 유통기한이 지나지 않은 lot의 (수량 − 예약 수량) 합.

## 4. 결정과 이유

### 4-1. 왜 변화량(+n, −n)이 아니라 다시 계산하나

변화량 방식(`available = available + Δ`)은 lot을 다시 읽지 않아 빠르다. 하지만 처리마다 Δ를 맞게 계산해야 하고(경과 lot이 끼면 틀리기 쉽다), 한 번 틀리면 그 오차가 영원히 쌓인다. 다시 계산하면 틀린 값이 생겨도 그 상품이 다음에 바뀔 때 저절로 맞아진다. 편의점 한 점포의 한 상품은 lot이 몇 개뿐이라 다시 계산하는 비용이 작다.

### 4-2. 왜 잠금 읽기(FOR SHARE)인가

쪽지끼리는 FIFO 그룹(점포)으로 줄을 서지만 수동 조정(S-14)은 줄 밖에서 바로 lot을 고친다. 그래서 조정과 쪽지 처리가 **같은 상품의 서로 다른 lot**을 동시에 바꿀 수 있다(같은 lot이면 낙관적 락이 잡는다).

MySQL의 일반 SELECT는 트랜잭션이 처음 무언가를 읽은 시점의 값을 보여 준다. 조정 트랜잭션이 먼저 읽어 둔 뒤 쪽지 처리가 다른 lot을 예약하고 커밋하면, 조정이 합산할 때 그 예약이 보이지 않는다. 조정이 나중에 커밋하면 조회 표는 예약이 빠진 낡은 합계가 된다.

`SELECT … FOR SHARE`는 최신 커밋 값을 읽고, 다른 트랜잭션이 그 lot을 고치는 중이면 끝날 때까지 기다렸다 읽는다.

`StoreStockTest.수동_조정과_쪽지_처리가_겹쳐도_조회표는_최신_합계다`가 이 상황을 그대로 만든다(오늘까지 lot 5개, 2027년 lot 10개 → 쪽지가 오늘까지 lot 2개 예약, 조정이 2027년 lot 1개 감소).

| | 조회 표 값 |
|---|---|
| 잠금 읽기 | (10 − 1) + (5 − 2) = **12** (맞음) |
| 일반 SELECT로 바꿔 돌려 보면 | (10 − 1) + 5 = **14** (예약 2개가 빠짐) |

드물게 두 처리가 서로의 lot을 기다리면(교착) MySQL이 한쪽을 되돌린다. 쪽지 쪽이면 SQS가 다시 보내고, 조정 쪽이면 409 `LOT_CHANGED`로 점주가 다시 한다. 상품을 늘 같은 순서(ID 오름차순)로 읽어 교착을 줄인다.

### 4-3. 왜 "값이 맞는 시각"(valid_until)이 필요한가

lot은 쪽지가 없어도 시간이 지나면 경과가 되어 구매 가능 수량에서 빠진다. 조회 표는 쪽지가 올 때만 바뀌므로 이 순간을 모른다. 그래서 계산할 때 "남은 재고가 있는 미경과 lot 중 가장 빠른 유통기한"을 같이 적어 둔다. 이 시각까지는 값이 맞다.

이 시각이 지난 행은 **품절로 보여 준다.** 실제보다 적게 보일 수는 있어도(최대 1분) 지난 재고가 보이지는 않는다. 덜 파는 쪽으로 틀리는 것이라 안전하다. 실제 예약은 쓰기 쪽(lot)에서 다시 검사하므로 조회 표가 어떻든 초과 판매는 생기지 않는다.

다른 방법과 비교:

| 방법 | 고르지 않은 이유 |
|---|---|
| 읽을 때 지난 행만 lot에서 다시 계산 | 정확하지만 "고객 목록은 조회 표만 읽는다"에 예외가 생긴다. 별도 서비스로 나누면 lot을 볼 수 없어 못 쓴다 |
| 1분 스케줄러만 (지난 행도 그대로 보여 줌) | 최대 1분 동안 지난 재고가 보인다 |
| 조회 표를 (점포, 상품, 기한) 단위로 | 언제나 정확하지만 lot 표의 복사본이 되어 나눈 의미가 약하다 |

**점주 재고 목록은 왜 이 방식을 쓰지 않았나.** 점주 목록에는 시간만 지나도 바뀌는 칸이 여럿이다(구매 가능, 임박 lot 수, 경과 lot 수, 부족). 바뀌는 시각도 칸마다 다르다(기한, 기한 − 24시간). 그리고 "임박만 보기" 같은 필터는 틀리면 빠져야 할 상품이 보이거나 보여야 할 상품이 빠져서 안전한 쪽이 없다. 그래서 점주 목록은 저장해 두지 않고 요청 때마다 lot을 SQL로 집계·검색·페이지로 자른다(`InventorySearchRepository`). 시간에 따라 바뀌는 값이 구매 가능 하나뿐이고 틀려도 덜 파는 쪽인 고객 목록만 조회 표를 쓴다.

### 4-4. 왜 이벤트 한 종류, 받는 곳 하나인가

재고를 바꾸는 곳은 여섯 군데(입고·예약·확정·해제·폐기·조정)지만 조회 표에 쓰는 곳은 `StoreStockProjector` 하나다. 각 처리는 "이 상품이 바뀌었다"만 알리고, 계산 규칙과 쓰기는 한 곳에 있다. 계산 규칙을 바꿀 때 여섯 군데를 고치지 않는다.

## 5. 미리 채우기와 SQL로 lot을 고칠 때

- V6 마이그레이션이 이미 있는 lot으로 조회 표를 채운다. 빈 표로 시작하면 dev·prod 고객 목록이 전부 품절로 보이기 때문이다. lot 기한은 한국 시각으로 저장되어 있어 지금 시각도 `CONVERT_TZ(UTC_TIMESTAMP(), '+00:00', '+09:00')`로 한국 시각을 만들어 비교한다.
- **lot을 SQL로 직접 고치면 조회 표가 따라오지 않는다.** 앱 코드는 lot을 바꾸면 끝에서 `StockChangePublisher.publish`를 부른다. 시험 정리 스크립트(`scripts/e01-cleanup.sql` 1-1)처럼 SQL로 고칠 때는 같은 트랜잭션에서 조회 표도 같은 식으로 다시 계산한다. 잊어도 그 상품이 다음에 바뀌면 맞아진다.
- 스케줄러의 상태 갱신(`markExpired`·`markImminent`)은 `status`만 바꾸고 수량은 바꾸지 않으므로 조회 표와 상관없다.

## 6. 별도 서비스로 나눈다면 (지금은 하지 않음)

지금은 같은 DB·같은 트랜잭션이라 조회 표가 쓰기와 항상 같이 커밋된다. 조회를 별도 서비스(store-query-service)로 나누면 바뀌는 것:

| 할 일 | 내용 |
|---|---|
| 이벤트 전달 | 스프링 이벤트 대신 outbox → 큐. `StockChanged` 모양은 그대로 쓴다(결과값이라 두 번 와도 같다) |
| 순서 | 큐에서는 이벤트 순서가 섞일 수 있다. 이벤트에 버전을 더하고 받는 쪽은 더 큰 버전만 반영한다 |
| 옮길 것 | `StoreStockProjector`·조회 표·조회 API를 새 서비스로. 정리 작업은 쓰기 쪽이 기한이 지날 때 이벤트를 내는 방식으로 바꾼다 |
| 바뀌는 성질 | 고객 화면이 잠깐 늦게 바뀐다(결과적 일관성). 예약은 여전히 쓰기 쪽이 검사하므로 초과 판매는 없다 |
| 다른 사람 일 | 쪽지 형식(common, `message-spec`), 새 서비스 배포·큐·권한, gateway `/stores/**` 경로 |

## 7. 받을 만한 질문

- **상품 30개인데 왜 조회 표를 따로 뒀나?** 지금 규모에서는 성능보다 구조를 보여 주려는 것이다. 고객 조회가 쓰기 표(lot)를 매번 합산하지 않게 나눴고, 나중에 조회만 따로 키우거나 서비스를 나눌 수 있는 자리를 만들었다.
- **둘이 어긋나지 않나?** 같은 트랜잭션에서 같이 바뀌어서 어긋나지 않는다. 예외는 시간이 지나 경과가 되는 경우 하나인데, 그때는 안전한 쪽(품절)으로 보여 주고 1분 안에 바로잡는다.
- **조회 표가 틀리면 초과 판매가 생기나?** 아니다. 예약은 언제나 lot을 다시 읽어 검사한다. 조회 표는 화면에 보여 주는 숫자일 뿐이다.
- **왜 잠금 읽기인가, 느리지 않나?** 4-2. 같은 상품을 동시에 고치는 경우에만 잠깐 기다린다. 쪽지끼리는 FIFO로 이미 줄을 서므로 대부분은 기다릴 일이 없다.
- **왜 커밋 뒤(`@TransactionalEventListener`)에 갱신하지 않았나?** 커밋과 갱신 사이에 파드가 죽으면 갱신이 빠진다. 같은 트랜잭션이면 둘 다 되거나 둘 다 안 된다.
