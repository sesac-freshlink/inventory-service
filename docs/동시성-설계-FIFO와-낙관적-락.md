# 동시성 설계: FIFO 그룹과 낙관적 락 (E-01, S-14)

재고 10개 lot에 1개짜리 예약 20건이 한꺼번에 들어오면 맞는 답은 성공 10, 실패 10이다. 이 문서는 같은 점포 쪽지를 한 줄로 세우지 않으면 무엇이 깨지는지 실험으로 보이고, 이 서비스가 그 문제를 어떻게 막는지 정리한다.

## 1. 무엇이 깨지나

예약은 "lot을 읽는다 → 남은 수량을 계산한다 → 예약 수량을 쓴다" 세 단계다. 두 처리가 같은 lot을 동시에 읽으면 둘 다 같은 값을 보고 계산한다. 뒤에 쓴 값이 앞에 쓴 값을 덮어써서 한 건이 사라진다. 이것을 갱신 손실(lost update)이라 한다.

## 2. 실험 결과

`FifoExperimentTest`가 네 가지 방식을 같은 조건(재고 10, 주문 20)으로 비교한다. 1~3은 모든 처리가 lot을 읽은 뒤에 쓰도록 맞춰서(CyclicBarrier) 순서 보장이 없을 때의 가장 나쁜 겹침을 매번 똑같이 만든다.

| 실험 | 방식 | 결과 | 뜻 |
|---|---|---|---|
| 1 | 락 없이 읽고 계산한 값을 그대로 쓴다 (`reserved = 읽은 값 + 1`) | 20건 모두 성공 응답, lot 예약 수량 1 | 19건이 사라졌다. 재고 10개를 20명에게 팔았다고 답했다. 오류가 나지 않아 아무도 모른다 |
| 2 | 1과 같은데 쓰기만 더하기로 (`reserved = reserved + 1`) | 성공 10, CHECK 제약 오류 10 | `chk_lot_reserved`(예약 ≤ 실물)가 11번째부터 막았다. 숫자는 맞지만 10건은 앱 검사를 통과하고도 DB에서 터졌다 |
| 3 | 실제 `handle()` 8건을 동시에 | 먼저 커밋한 1건만 반영, 7건은 `ObjectOptimisticLockingFailureException`으로 통째로 되돌림. 다시 처리하면 성공 10, 실패 10 | `inventory_lot.version`이 겹침을 찾았다. 틀린 값은 남지 않지만 8건 중 7건이 헛일이 됐다 |
| 4 | 실제 `handle()`을 하나씩 (= FIFO 그룹 안) | 예외 없이 성공 10, 실패 10 | 앞 처리가 커밋한 뒤에 다음 처리가 읽으므로 겹칠 일이 없다 |

## 3. 이 서비스의 답

1. **FIFO 메시지 그룹 = storeId.** 같은 점포 쪽지는 SQS가 한 번에 하나씩만 내준다. 실험 4처럼 겹칠 일 자체가 없어서 DB 락 없이도 맞다. 점포가 다르면 lot도 달라서 파드 2개가 동시에 처리해도 된다.
2. **CHECK 제약은 마지막 방어선.** `quantity ≥ 0`, `reserved ≤ quantity`. 코드에 실수가 있어도 음수 재고는 DB가 거부한다(실험 2).
3. **낙관적 락(`@Version`)은 쪽지 밖 변경용.** 점주 수동 조정(S-14)은 쪽지 줄에 서지 않고 바로 lot을 고친다. 그래서 같은 lot의 쪽지 처리와 겹칠 수 있고, 이때만 version이 일한다.
   - 조정이 늦게 커밋하면: `UPDATE ... WHERE version = 읽은 값`이 0행이라 409 `LOT_CHANGED`. 점주가 바뀐 수량을 보고 다시 한다.
   - 쪽지 처리가 늦게 커밋하면: processed_message 기록·예약·결과 쪽지까지 한 트랜잭션이라 전부 되돌려진다. 리스너가 예외를 던지면 SQS가 같은 쪽지를 다시 보내고, 그때는 바뀐 수량으로 처리된다. `AdjustmentTest`가 두 경우를 트랜잭션 두 개를 엇갈리게 만들어 확인한다.

## 4. 왜 비관적 락(`SELECT ... FOR UPDATE`)을 쓰지 않았나

- 쪽지끼리는 FIFO가 이미 줄을 세우므로 락이 할 일이 없다. 모든 예약 처리에 락을 걸면 겹치지도 않는데 비용만 든다.
- 겹칠 수 있는 곳은 수동 조정 하나이고 드물다. 드문 충돌에는 기다리게 하는 락보다 "겹치면 한쪽이 다시 한다"가 단순하다.
- 비관적 락을 넣으려면 예약·확정·해제·폐기 조회를 모두 잠금 조회로 바꿔야 한다. 고칠 곳과 교착(deadlock) 걱정이 늘어난다.

## 5. 한계

- 수동 조정과 쪽지 처리가 겹치면 한쪽은 실패한다. 조정은 점주가 다시 누르고, 쪽지는 SQS가 다시 보낸다. 쪽지가 3번 연속 겹쳐 실패하면 DLQ로 간다([실패-시나리오-절차.md](실패-시나리오-절차.md)). 조정은 사람이 누르는 일이라 이렇게 될 가능성은 낮다.
- 스케줄러의 상태 갱신(`markExpired`·`markImminent`)은 대량 UPDATE라 version을 올리지 않는다. 표시용 `status`만 바꾸고 판단에는 쓰지 않으므로 겹쳐도 수량은 틀리지 않는다.

## 6. 직접 돌려 보기

```bash
./gradlew test --tests '*FifoExperimentTest'
```

Docker가 켜져 있어야 한다(Testcontainers MySQL). 숫자는 `build/reports/tests/test/index.html`의 FifoExperimentTest → Standard output에서 `[실험 1]`~`[실험 4]` 줄로 본다.

## 7. 발표용 한 줄

> 같은 lot을 동시에 고치면 갱신 손실로 재고 10개를 20명에게 판다는 것을 실험으로 확인했다. 그래서 점포 ID를 SQS FIFO 메시지 그룹으로 써서 같은 점포 쪽지를 한 줄로 세웠고, 쪽지를 거치지 않는 수동 조정에만 낙관적 락을 걸었다. 겹치면 조정은 409로, 쪽지는 SQS 재전송으로 다시 처리된다.
