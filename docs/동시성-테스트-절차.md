# 동시 예약 100건 시험 절차 (T-22, E-01)

같은 점포·상품에 RESERVE 쪽지 100건을 한꺼번에 넣고, 재고가 음수가 되지 않고 성공 수가 처음 재고와 같은지 확인한다. 실제 투입은 사람이 dev SQS·RDS로 한다. 자동 테스트(Testcontainers)는 쪽지 하나하나의 처리만 보고, 이 시험은 큐를 거친 실제 흐름을 본다.

명령은 Windows PowerShell 5.1 기준이다. AWS 로그인·포트 포워딩·실행 구성은 [개발 환경 접속 가이드](https://github.com/sesac-freshlink/.github/blob/main/docs/개발환경-접속.md) 1~4장을 따른다. 비밀값은 이 문서에 적지 않는다.

## 1. 왜 음수가 안 되나

- 같은 점포 쪽지는 FIFO 큐의 같은 메시지 그룹(storeId)이라 SQS가 한 번에 하나만 내준다. 파드가 2개여도 같다. 그래서 DB 락 없이도 같은 lot을 동시에 건드리지 않는다.
- 쪽지 하나는 한 트랜잭션에서 `processed_message` 기록 → lot 예약 → `reservation` 저장 → 결과 쪽지 outbox 저장을 한다.
- 마지막 방어선으로 DB CHECK `chk_lot_reserved (reserved_quantity >= 0 AND reserved_quantity <= quantity)`가 있다.

## 2. 파일

| 파일 | 하는 일 |
|---|---|
| `scripts/e01-reserve-100.ps1` | RESERVE 쪽지를 10건씩 `send-message-batch`로 보낸다. orderId `900001~900100`, messageId 새 GUID, 그룹 ID = storeId, 중복 제거 ID = messageId |
| `scripts/e01-check.sql` | lot 수량, 예약 상태별 건수, RESERVED/RESERVE_FAILED 건수와 처리 시간, 불변식(예약 합 ≤ 실물 합), 음수 lot을 본다. 읽기만 한다 |
| `scripts/e01-cleanup.sql` | 시험 주문의 예약만 지우고 lot `reserved_quantity`를 되돌린다. 조건 있는 UPDATE·DELETE만 쓰고 마지막 COMMIT은 사람이 친다 |

## 3. 준비

1. 접속 가이드 2장대로 DB 포트 포워딩 창을 연다.
2. PC inventory를 `QUEUE_PREFIX=dev-taewoo-`로 띄운다(접속 가이드 3장). 로그에 `Started InventoryServiceApplication`이 보여야 한다.
   - 파드 2개 상황을 흉내 내려면 같은 설정으로 하나 더 띄운다(두 번째 실행 구성에 `SERVER_PORT=8081`). FIFO 그룹이 같아 둘이 나눠 가져가도 순서는 지켜진다.
3. 시험할 상품을 하나 고른다. 이미 예약·재고가 있는 상품이면 결과 해석이 어려우므로 시험 전용으로 쓸 상품(예: productId 15 = `P015`)을 정하고, 그 상품의 현재 lot을 `e01-check.sql` 1번으로 먼저 본다.
4. 재고 N개를 입고한다. 접속 가이드 4-1처럼 INBOUND 쪽지를 개인 큐에 보낸다. 유통기한은 시험 날짜보다 뒤로 둔다(경과 lot은 예약에서 빠진다).

   ```powershell
   $env:AWS_PROFILE = "freshlink-dev"
   $id = [guid]::NewGuid().ToString()
   $now = [DateTimeOffset]::Now.ToOffset([TimeSpan]::FromHours(9)).ToString("yyyy-MM-ddTHH:mm:sszzz")
   $exp = (Get-Date).AddMonths(2).ToString("yyyy-MM-dd")      # 실행일보다 뒤인 유통기한
   $ship = "SHP-E01-100-" + (Get-Date -Format "yyyyMMddHHmmss")
   @"
   {"messageId":"$id","type":"INBOUND","createdAt":"$now","storeId":1,"shipmentId":"$ship","items":[{"productCode":"P015","quantity":30,"expiryDate":"$exp"}]}
   "@ | Set-Content inbound-e01.json -Encoding Ascii

   $q = aws sqs get-queue-url --queue-name dev-taewoo-inventory-commands.fifo --query QueueUrl --output text
   aws sqs send-message --queue-url $q --message-body file://inbound-e01.json --message-group-id 1 --message-deduplication-id $id
   ```

   `e01-check.sql` 1-1번 `reservable`이 N(위 예시는 30)인지 확인한다. 이 값이 처음 재고다. 1번 표의 `available` 합은 기한 지난 lot까지 더하므로 N으로 쓰지 않는다(`expired = 1`인 lot은 예약에서 빠진다).

## 4. 투입

투입 직전에 아래를 실행한다.

```sql
SELECT (SELECT COALESCE(MAX(id), 0) FROM outbox)      AS outbox_from,
       (SELECT COALESCE(MAX(id), 0) FROM reservation) AS reservation_from,
       (SELECT COUNT(*) FROM reservation
        WHERE order_id BETWEEN 900001 AND 900100)     AS existing_in_range;   -- 범위는 투입할 orderId에 맞춘다
```

- `existing_in_range`가 0이 아니면 **투입하지 않는다.** 이전 시험이 남은 것이면 6장 정리를 먼저 하고, 다른 주문이면 `-OrderIdBase`로 겹치지 않는 범위를 쓴다. 정리 SQL이 시험 주문이 아닌 예약을 건드리지 않게 하려는 확인이다.
- `outbox_from`·`reservation_from`은 5장 check SQL과 6장 정리 SQL의 같은 이름 변수에 넣는다. 정리 SQL은 outbox를 지우지 않으므로, 다시 시험할 때 이전 결과가 섞이지 않게 이번 투입 뒤에 생긴 행만 센다.

```powershell
$env:AWS_PROFILE = "freshlink-dev"
.\scripts\e01-reserve-100.ps1 -StoreId 1 -ProductId 15 -Quantity 1 -Count 100 -QueuePrefix dev-taewoo-
```

- 먼저 `-DryRun`을 붙여 돌리면 보내지 않고 배치 JSON 파일만 만든다. 끝에 찍히는 `배치 파일` 폴더에서 내용을 볼 수 있다.
- 끝에 `보낸 건수 : 100 / 100 (실패 0)`이 나와야 한다. 실패가 있으면 경고 줄에 코드가 찍히고 종료 코드가 1이다.
- 공용 큐(`-QueuePrefix dev-`)는 dev 클러스터 파드가 읽으므로 스크립트가 막는다.
- 같은 orderId로 두 번 투입하면 두 번째는 "같은 주문 재수신"으로 처리돼 RESERVED만 다시 나간다. 다시 시험하려면 6장 정리를 먼저 한다.

## 5. 결과 확인

`e01-check.sql` 맨 위 여섯 값(`@store_id`, `@product_id`, `@order_from`, `@order_to`, `@outbox_from`, `@reservation_from`)을 맞추고 실행한다. 3번 결과의 `orders` 합이 100이 될 때까지 몇 초 간격으로 다시 돌린다.

결과 표 양식(포트폴리오·보고용). 아래 기대값은 `-Quantity 1`이고 처음 재고 N이 보낸 건수(100) 이하일 때다. 수량을 바꾸면 성공 수는 `min(100, floor(N / 수량))`이고, 남은 재고가 요청 수량보다 적으면 실패 쪽지의 `availableQuantity`가 0이 아닐 수 있다.

| 항목 | 기대 | 결과 | 근거 |
|---|---|---|---|
| 보낸 쪽지 | 100 | | 스크립트 출력 |
| 처음 재고 N | (준비 4번 값) | | check 1-1번 `reservable`(투입 전) |
| 성공(RESERVED 주문 수) | N | | check 3번 RESERVED `orders` |
| 실패(RESERVE_FAILED 주문 수) | 100 − N | | check 3번 RESERVE_FAILED `orders` |
| 실패 사유 | 전부 OUT_OF_STOCK, availableQuantity 0 | | check 5번 |
| 예약 합 ≤ 실물 합 | ok = 1 | | check 6번 |
| 음수·초과 lot | 0행 | | check 7번 |
| 예약 표 = lot 예약 수량 | diff = 0 | | check 8번 |
| 처리 시간 | (측정값) ms | | check 4번 `elapsed_ms` |
| 컨슈머 수 | 1 또는 2 | | 띄운 PC 인스턴스 수 |

- 처리 시간은 첫 결과 쪽지부터 마지막 결과 쪽지까지 DB 시각 차이다. 보낸 시각(스크립트 출력)과 함께 적는다.
- 결과 화면을 캡처해 둔다.

## 6. 정리

1. 결과를 캡처한 뒤 `e01-cleanup.sql`의 `@store_id`, `@order_from`, `@order_to`, `@reservation_from`(4장에서 받은 값)을 맞춘다.
2. 0번 미리 보기 결과가 시험 주문만인지 본다.
3. 1~3번을 실행하고, 3번 확인 결과가 0행이면 `COMMIT;`, 아니면 `ROLLBACK;`을 직접 친다.
   - MySQL Workbench의 safe update 모드에서 1175 오류가 나면 그 세션에서만 `SET SQL_SAFE_UPDATES = 0;` 뒤 다시 실행한다.
4. outbox·processed_message 행과 개인 결과 큐(`dev-taewoo-inventory-results`)에 쌓인 결과 쪽지는 지우지 않는다. 결과 큐는 보존 기간이 지나면 SQS가 지운다. 큐 purge는 하지 않는다.
5. 입고한 재고(lot 수량)는 남는다. 다음 시험 때 그대로 쓰거나 폐기 API로 줄인다.

## 7. 포트폴리오에 적을 문장 예시

> 같은 점포·상품에 주문 100건을 동시에 넣는 시험에서 재고 30개 중 정확히 30건만 예약되고 70건은 재고 부족으로 거절됐다. 음수 재고는 0건이었고 100건을 처리하는 데 약 OOO ms가 걸렸다. 점포 ID를 SQS FIFO 메시지 그룹으로 써서 같은 점포 쪽지가 하나씩 처리되게 했기 때문에 DB 락 없이 정합성을 지켰다. 컨슈머를 2개로 늘려도 결과가 같았다.

숫자(30, 70, OOO ms, 컨슈머 수)는 실제 결과로 바꾼다.
